When tracing a loop manually, I record the values of the variables in the exact order the program executes them. For the Cisco lab 2.2.9 on finding positive powers of 2, for example, `result` begins as `1`, and the loop runs while `i < pow`. With `pow = 3`, the loop runs at `i = 0`, `i = 1`, and `i = 2`. Each iteration multiplies `result` by `2`, producing `2`, then `4`, then `8`. When `i` becomes `3`, the condition `3 < 3` is false, so the loop stops.

```cpp
for ( int i = 0; i < pow; i++) {

    result*= 2;

}
```

| `i` | `result` after `result *= 2` |
| --: | ---------------------------: |
|   0 |                            2 |
|   1 |                            4 |
|   2 |                            8 |

I compared my manual trace with an AI-generated trace. The AI trace was accurate because it preserved the program state at every step: it began with `result = 1`, showed three iterations, and included the final failed condition when `i = 3`. A trace table should show how variables change step by step, not only provide the final result.

A difference that would reveal an AI error would be showing four iterations, using `i = 3` as a valid loop iteration, or changing `result` to `16`. Even if the AI gave the correct output sometimes, an incorrect intermediate state would show that it did not truly follow the loop’s execution.
